# Environment and dependency stack (2026-09-20)

## What changed and why

Everyone now works in the repo's own `.venv`, installed from a pinned
lockfile. Before this, dependencies were open ranges (`pandas>=2.2`) with no
venv, so each of us got whatever pip resolved on the day. That surfaced
concretely: `ruff` was installed into a base conda environment and resolved to
0.16, while `requirements.txt` would have allowed 0.5 — two teammates would
have got different lint results on the same code.

Version drift matters more than it sounds. Lint noise is cosmetic, but a
pandas or pyarrow difference can change *results*, and CLAUDE.md asks for
reproducibility.

## How it is set up

- `make setup` creates `.venv` and installs `requirements.lock.txt`.
- Two dependency files, deliberately:
  - `requirements.txt` — direct dependencies, loose ranges. Says what the
    project needs. **Edit this one.**
  - `requirements.lock.txt` — all 140 packages pinned exactly, generated by
    `make lock`. Says what we are actually running. **Install from this one.**
- Adding a dependency: edit `requirements.txt`, run `make lock`, commit both.
  `make lock` resolves in a throwaway environment, so the lock reflects
  `requirements.txt` rather than whatever happens to be in your `.venv`.
- `make test` / `make lint` / `make corpus` call `.venv/bin/` explicitly, so
  they behave identically whether or not you activated the venv. Prefer them
  over bare `pytest` / `python`.

Python is **3.12.2** (via pyenv). Note that macOS system Python is 3.9, which
is below the 3.11+ floor — `make setup` will fail loudly rather than build a
venv on it.

## The stack was chosen by a resolver, not by us

Worth being explicit: nobody picked these versions. `pip` resolved them from
the open ranges, and `make lock` froze the result. The notable ones:

| Package | Pinned | Comment |
|---|---|---|
| pandas | 3.0.6 | major version bump; 2.x was what the ranges implied |
| numpy | 2.5.3 | |
| pyarrow | 25.0.1 | the corpus build is pure pyarrow, no pandas |
| seaborn | 0.13.2 | released well before pandas 3.0 |
| statsmodels | 0.15.0 | likewise |
| ruff | 0.16.8 | |
| pytest | 9.1.1 | |

pandas 3.0 was the concern: the pinned seaborn and statsmodels both predate it,
and those are exactly what the results and validation chapters depend on.

## So it was tested, 2026-09-20

A miniature version of the actual analysis path, on the real corpus schema:
`read_parquet`, a `groupby(["congress_number", "party"])` mean unstacked into
the per-party-position panel (RQ1/RQ2), the D–R distance per Congress, a
statsmodels OLS of score on party, and a seaborn `lineplot` over Congress with
a dashed break marker.

**All of it worked.** No errors, no warnings. So pandas 3.0 stays pinned —
there is now evidence against downgrading, and the reproducibility win comes
from pinning at all, not from which version.

## Two gotchas this exposed

Both will bite whoever writes the analysis code first:

1. **`date` reads back as `object`**, holding Python `datetime.date` objects —
   not `datetime64`. So `.dt` accessors, `resample`, and date-positioned plot
   axes all need `pd.to_datetime(df["date"])` first. This is not a pandas 3
   thing; pyarrow `date32` maps that way in 2.x too. It mostly will not matter
   because we aggregate by Congress, but it will the moment someone draws the
   January 3, 2017 break as a dated vertical line.
2. **`text` has pandas 3's new `str` dtype**, not `object`. Any 2.x-era idiom
   like `select_dtypes(include="object")` will silently find no text columns.

## Config files

`ruff.toml` sets `src = ["code"]` and `pytest.ini` sets `pythonpath = code`.
Both encode the same import root as the `sys.path` insert in `code/scripts/`,
which is what makes `from src.config import ...` resolve as first-party in all
three contexts. Without the ruff setting, ruff classifies our own modules as
third-party and demands they be grouped next to `pytest`.
